# BritMart Supplier System Detailed Database Schema

## 3.1 Purpose

This document defines the logical database schema for the BritMart Supplier and Procurement API.

The schema is designed for:

- Transactional integrity
- Incremental Microsoft Fabric extraction
- Auditability
- Idempotent processing
- Referential integrity
- Status-history preservation
- PostgreSQL production deployment
- SQLite-compatible local development where practical

PostgreSQL will be the target production-style database. SQLite may be used during early local development.


## 3.2 Data-Type Standards

| Business use | PostgreSQL type | Local-development treatment |
|---|---|---|
| Primary identifier | `UUID` | Stored as text-compatible UUID |
| Short code | `VARCHAR` | Text |
| Description | `TEXT` | Text |
| Quantity | `NUMERIC(18,3)` | Decimal-compatible value |
| Monetary value | `NUMERIC(18,4)` | Decimal-compatible value |
| Percentage/rate | `NUMERIC(9,6)` | Decimal-compatible value |
| Date | `DATE` | ISO-formatted date |
| Timestamp | `TIMESTAMPTZ` | UTC ISO timestamp |
| Boolean | `BOOLEAN` | Boolean/integer |
| Version number | `INTEGER` | Integer |
| JSON metadata | `JSONB` | JSON text where required |

All application timestamps must be stored in UTC.

Python `Decimal` must be used for monetary values and controlled quantities. Python floating-point values must not be used for money.


## 3.3 Naming Standards

- Database tables use lowercase `snake_case`.
- Primary keys use `<entity>_id`.
- Foreign keys use the referenced primary-key name.
- Business codes use `<entity>_code`.
- Timestamps use `_at`.
- Dates use `_date`.
- Boolean columns use `_flag` or `is_`.
- Current operational tables contain `created_at` and `updated_at`.
- Incrementally extracted tables use a stable ordering of `updated_at` followed by the primary key.
- Important operational tables include `version_number` for optimistic concurrency.


# 3.4 Reference Tables

## 3.4.1 `product_reference`

A synchronised reference copy of product information mastered in the SQL operational system.

| Column | Type | Null | Constraint or purpose |
|---|---|---:|---|
| `product_id` | UUID | No | Primary key; generated by the SQL source system |
| `sku` | VARCHAR(40) | No | Unique product stock-keeping unit |
| `product_name` | VARCHAR(200) | No | Product description |
| `category_id` | UUID | No | External category identifier |
| `subcategory_id` | UUID | No | External subcategory identifier |
| `storage_type` | VARCHAR(20) | No | `AMBIENT`, `CHILLED` or `FROZEN` |
| `unit_of_measure` | VARCHAR(20) | No | Unit, kilogram, litre, case or similar |
| `case_pack_quantity` | NUMERIC(18,3) | No | Must be greater than zero |
| `shelf_life_days` | INTEGER | Yes | Required where applicable |
| `active_flag` | BOOLEAN | No | Defaults to `TRUE` |
| `source_updated_at` | TIMESTAMPTZ | No | Update time in authoritative SQL source |
| `synchronised_at` | TIMESTAMPTZ | No | Time copied into FastAPI reference store |
| `created_at` | TIMESTAMPTZ | No | Local row creation time |
| `updated_at` | TIMESTAMPTZ | No | Local row update time |

Constraints:

- `sku` must be unique.
- `case_pack_quantity > 0`.
- `shelf_life_days >= 0` when populated.
- FastAPI cannot independently change authoritative product attributes.

Indexes:

```text
UNIQUE (sku)
INDEX (updated_at, product_id)
INDEX (category_id, subcategory_id)
INDEX (active_flag)
````

| `country_code`            | CHAR(2)      |   No | Two-character country code    |
| `default_currency_code`   | CHAR(3)      |   No | Transaction currency          |
| `standard_lead_time_days` | INTEGER      |   No | Must be zero or greater       |

| `supports_chilled`        | BOOLEAN      |   No | Defaults to `FALSE`           |
| `supports_frozen`         | BOOLEAN      |   No | Defaults to `FALSE`           |

```text
ACTIVE
```

# 3.6 Purchase-Order Tables

## 3.6.1 `purchase_order`

Stores each purchase-order header.

| Column                    | Type          | Null | Constraint or purpose                        |
| ------------------------- | ------------- | ---: | -------------------------------------------- |
| `purchase_order_id`       | UUID          |   No | Primary key                                  |
| `purchase_order_number`   | VARCHAR(30)   |   No | Unique business number                       |
| `supplier_id`             | UUID          |   No | Foreign key to `supplier`                    |
| `distribution_centre_id`  | UUID          |   No | Foreign key to distribution-centre reference |
| `order_date`              | DATE          |   No | Purchase-order date                          |
| `requested_delivery_date` | DATE          |   No | Requested delivery date                      |
| `expected_delivery_date`  | DATE          |   No | Confirmed expected date                      |
| `currency_code`           | CHAR(3)       |   No | One currency per purchase order              |
| `purchase_order_status`   | VARCHAR(30)   |   No | Controlled status                            |
| `subtotal_amount`         | NUMERIC(18,4) |   No | Defaults to zero                             |
| `tax_amount`              | NUMERIC(18,4) |   No | Defaults to zero                             |
| `total_amount`            | NUMERIC(18,4) |   No | Subtotal plus tax                            |
| `approved_by`             | VARCHAR(100)  |  Yes | Required after approval                      |
| `approved_at`             | TIMESTAMPTZ   |  Yes | Required after approval                      |
| `cancelled_at`            | TIMESTAMPTZ   |  Yes | Required if cancelled                        |
| `cancellation_reason`     | VARCHAR(500)  |  Yes | Required if cancelled                        |
| `created_at`              | TIMESTAMPTZ   |   No | Creation time                                |
| `updated_at`              | TIMESTAMPTZ   |   No | Latest update time                           |
| `version_number`          | INTEGER       |   No | Defaults to `1`                              |

Permitted statuses:

```text
DRAFT
APPROVED
PARTIALLY_SHIPPED
FULLY_SHIPPED
PARTIALLY_RECEIVED
COMPLETED
CANCELLED
CLOSED_WITH_SHORTFALL
```

Constraints:

* `purchase_order_number` must be unique.
* Supplier must exist and be permitted for ordering.
* Distribution centre must exist and be active.
* `requested_delivery_date >= order_date`.
* `expected_delivery_date >= order_date`.
* `subtotal_amount >= 0`.
* `tax_amount >= 0`.
* `total_amount = subtotal_amount + tax_amount`.
* Approved orders require `approved_by` and `approved_at`.
* Cancelled orders require `cancelled_at` and `cancellation_reason`.

Indexes:

```text
UNIQUE (purchase_order_number)
INDEX (supplier_id, order_date)
INDEX (distribution_centre_id, expected_delivery_date)
INDEX (purchase_order_status)
INDEX (updated_at, purchase_order_id)
```

Stores products and quantities ordered on a purchase order.

| Column                          | Type          | Null | Constraint or purpose            |
| ------------------------------- | ------------- | ---: | -------------------------------- |

| `purchase_order_id`             | UUID          |   No | Foreign key to purchase order    |
| `line_number`                   | INTEGER       |   No | Sequential line number           |
| `product_id`                    | UUID          |   No | Foreign key to product reference |

| `ordered_quantity`              | NUMERIC(18,3) |   No | Must be greater than zero        |
| `cancelled_quantity`            | NUMERIC(18,3) |   No | Defaults to zero                 |
| `unit_cost`                     | NUMERIC(18,4) |   No | Agreed unit cost                 |
| `tax_rate`                      | NUMERIC(9,6)  |   No | Tax rate as a controlled decimal |
| `line_subtotal`                 | NUMERIC(18,4) |   No | Quantity multiplied by unit cost |
| `line_tax`                      | NUMERIC(18,4) |   No | Calculated tax                   |
| `line_total`                    | NUMERIC(18,4) |   No | Subtotal plus tax                |
| `line_status`                   | VARCHAR(30)   |   No | Controlled line status           |
| `created_at`                    | TIMESTAMPTZ   |   No | Creation time                    |
| `updated_at`                    | TIMESTAMPTZ   |   No | Latest update time               |

```text
OPEN
PARTIALLY_SHIPPED
FULLY_SHIPPED
PARTIALLY_RECEIVED
COMPLETED
CANCELLED
CLOSED_WITH_SHORTFALL
```

Constraints:

* Foreign key to `purchase_order`.
* Foreign key to `product_reference`.
* Foreign key to `supplier_product_agreement`.
* Unique combination of `purchase_order_id` and `line_number`.
* `ordered_quantity > 0`.
* `cancelled_quantity >= 0`.
* `cancelled_quantity <= ordered_quantity`.
* `unit_cost >= 0`.
* `tax_rate >= 0`.
* Product and supplier agreement must match the purchase-order supplier.

Indexes:

```text
UNIQUE (purchase_order_id, line_number)
INDEX (purchase_order_id)
INDEX (product_id)
INDEX (supplier_product_agreement_id)
INDEX (updated_at, purchase_order_line_id)
```

| `dispatch_at`            | TIMESTAMPTZ  |  Yes | Required when dispatched              |

```text
CREATED
DISPATCHED

REJECTED
CANCELLED
```

```text
AMBIENT
CHILLED
FROZEN
MIXED
```

Constraints:

* `shipment_number` must be unique.

# 3.11 Incremental Extraction Index Standard

Every entity extracted incrementally by Fabric must have an index beginning with:

```text
(changed_at, history_primary_key)
```


# 3.12 Delete Strategy

Physical deletion is not permitted for important operational records after they have participated in a business transaction.

Use:

* `active_flag = FALSE`
* `INACTIVE`
* `CANCELLED`
* `TERMINATED`
* `EXPIRED`

Reference synchronisation may include a logical deletion indicator so Fabric can detect records removed from the authoritative source.


# 3.13 Transaction Boundaries

The following operations must be atomic:

1. Creating a purchase order and all its lines.
2. Approving a purchase order and recording status history.
3. Cancelling a purchase order and recording status history.
4. Creating a shipment and its shipment lines.
5. Changing shipment status and recording status history.
6. Creating an idempotency record with the protected resource.
7. Updating calculated purchase-order totals following line changes.

If any part fails, the complete transaction must roll back.


# 3.14 Database Migration Strategy

Database changes will be managed using Alembic migrations.

Migration requirements:

* Every structural change must have a migration.
* Migrations must be version controlled.
* Destructive migrations require explicit review.
* Production data must not be silently dropped.
* Schema upgrades must be tested against populated data.
* Roll-forward recovery is preferred for production.
* Seed data must be separated from schema migrations.


# 3.15 Schema Acceptance Criteria

The schema is accepted when:

* Every Phase 1 entity maps to a defined table.
* All primary and foreign keys are specified.
* Monetary and quantity precision is controlled.
* Incremental extraction columns are indexed.
* Status values are controlled.
* Important business constraints are enforceable.
* Status history is append-only.
* Idempotency is supported.
* API secrets are never stored in plain text.
* FastAPI and SQL warehouse ownership remain separated.
* Goods-receipt reconciliation fields align with shipment fields.
* Schema changes can be managed through migrations.
